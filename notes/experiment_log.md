# Experiment log

Every setting, number and problem, in order. Numbers come from `results/*.csv` (generated by scripts, not typed).

## Environment
- Laptop: MacBook (Apple Silicon, **8 GB RAM**), conda env `llie` (Python 3.10, PyTorch 2.14.1).
- GPU work: Kaggle, **Tesla T4** (x1 or x2), PyTorch 2.11.0+cu128. Retinexformer paper used PyTorch 1.11.
- Mac pitfalls found (all verified by direct CPU-vs-MPS comparison):
  - LLFormer outputs are wrong on MPS (−2 dB) → CPU. YOLOv8 mAP is wrong on MPS (0.42 vs 0.65) → CPU/CUDA.
  - pyiqa NIQE needs float64 (not on MPS) → CPU. Large images swap the 8 GB Mac → `torch.mps.empty_cache()`.
  - All Mac timings unreliable (swap) → every speed number in the report is from one Kaggle T4.

## 1. Re-training Retinexformer from scratch (LOL-v1)
| Setting | Value |
|---|---|
| Config | official `Options/RetinexFormer_LOL_v1.yml`, unchanged except `num_worker_per_gpu` 8→4, `save_checkpoint_freq` 1e3→5e3 |
| Iterations | 150,000 (full schedule), batch 8, patch 128, Adam lr 2e-4, cosine-restart schedule, L1, mixup |
| Hardware / time | Kaggle T4, 2 sessions (135k + 15k, auto-resume), ~0.28 s/iter, **~11.9 GPU h** |
| Seed | 100 (config default) |

**Result (LOL-v1, our `evaluate.py`):** final model **23.10 dB / 0.828 SSIM / 0.143 LPIPS**;
best-on-test checkpoint (94k) 23.61 dB. Released weights: **25.15 / 0.843 / 0.131**; paper: 25.16 / 0.845.
Our evaluation reproduces the training log's PSNR exactly (23.0969), so the gap is not a metric difference.
LOL-v2-syn (cross-dataset, LOL-v1 weights): 15.65 dB. NIQE: LIME 3.94, DICM 3.59, MEF 3.51 (released: 4.07 / 3.42 / 3.44).

**Gap of ~2 dB — likely reasons (not proven):**
1. Same gap reported independently: GitHub issue #132 ("Unable to reproduce", 23.45 dB on LOL-v1, closed without
   explanation). So it is not specific to our setup.
2. The released weights may be a best-of-several-runs / best checkpoint; ours is the final model.
3. PyTorch 2.11 vs 1.11, different GPU, random seed - LOL-v1 has only 485 training and 15 test images, so
   run-to-run variance is large (validation PSNR moved ±0.3 dB between consecutive 1k checkpoints).
4. Validation PSNR plateaued at ~23.1 dB from ~110k iterations on (`results/figures/training_val_psnr.png`),
   so "more iterations" is unlikely to close the gap.

**Problems hit:** `setup.py develop` fails on new setuptools (→ `PYTHONPATH`); BasicSR names the experiment
after the yml FILE not its `name:` (→ folder `RetinexFormer_LOL_v1`); resume failed on PyTorch ≥2.6
(`torch.load` weights_only default → `weights_only=False` for our own `.state`); first Kaggle run had no GPU.

## 2. Baselines — protocol notes
- Classical (HE, CLAHE, Gamma 0.4) on the L channel of LAB (colour preserved); Zero-DCE (`Epoch99.pth`), SCI
  (`medium.pt`), LLFormer (LOL weights), Retinexformer (dataset-matched released weights) all run by us.
- SNR-Aware: images released by the authors (Retinexformer README Drive) — reproduces the paper exactly.
- GSAD: run by us on Kaggle. Its test script always rescales outputs to the **ground truth's mean brightness**.
  We report the raw output (main) and the adjusted output (reference only). The trick adds 4–8.5 dB.
- **LOL-v2-real leaks LOL-v1 training data:** 91/100 test images identical to LOL-v1 train images
  (thumbnail comparison). Any LOL-v1-trained model is not evaluated on LOL-v2-real.
- Unpaired sets use LOL-v1 weights for Retinexformer-based models.

## 3. Detection (ExDark, YOLOv8m COCO-pretrained, no fine-tuning)
- ExDark official TEST split, 100 images/class (seed 0) = 1,200 images, 3,776 boxes, ≤1024 px, EXIF orientation

## 4. Fine-tuning experiment (my contribution) — runs A–D
| Setting | Value (all runs) |
|---|---|
| Start weights | released Retinexformer `LOL_v1.pth` |
| Data | LOL-v1 **train** only (485 pairs), random 128×128 crops + h/v flips, **identical pre-computed batch schedule** for every run (seed 42) |
| Iterations / batch | 10,000 / 8 |
| Optimiser | Adam (0.9, 0.999), lr 2e-5 → 1e-6 cosine, grad-norm clip 0.01 (as BasicSR) |
| SNR loss | α = 1.0, rank-normalised SNR, weights divided by their mean (avg weight = 1) |
| FFT loss | weight 0.05, L1 between `rfft2` amplitudes (ortho) |
| Evaluation | **final** weights only; LOL-v1, LOL-v2-syn, LIME/DICM/MEF, ExDark-200 (YOLO on one T4). Not LOL-v2-real (leak). |
| Hardware | Kaggle 2×T4: A+B in parallel, then C+D |

**Design decision (measured, explain in viva):** the plan's min-max normalisation of the SNR map gave
weight > 1.9 to **96%** of pixels (raw SNR on LOL-v1: median ~10, max ~1,500), i.e. the "SNR loss" ≈ 2×L1 —
a disguised 2× learning rate, which would confound A vs B. With rank normalisation + mean-1 weights, the
weights span 0.67–1.33, average exactly 1, and the darkest 30% of pixels get mean weight 1.13 vs 0.94 elsewhere.

**Verification:** smoke test on the Mac (20 iters, all 4 losses): at iteration 10 the plain L1 was identical in
every run (0.03221) → identical batches confirmed. `final.pth` loads in `retinexformer_infer.py`.

**Incident (2026-10-08) — first run used the WRONG start weights; re-run.**
The first Kaggle run of A–D started from `LOL_v2_real.pth`, not `LOL_v1.pth`: when looking up Google Drive file IDs
I paired each file name with the *next* entry's ID. Symptoms that exposed it: training L1 at the start was 0.088
instead of 0.041; after fine-tuning, PSNR dropped on LOL-v1 *training* images too (26.6 → 22.3 dB); all four runs
ended at ~22.7 dB on LOL-v1 whatever the loss; a "pretrained" ExDark row differed between Kaggle (0.664) and the Mac (0.628).
How it was found: (1) devices ruled out — Mac-CPU and Kaggle-GPU YOLO agree on the same images (raw 0.707/0.706,
A 0.661/0.661, B 0.658/0.658); MPS and CPU enhancement agree to 1 grey level; (2) md5 of Kaggle's "LOL_v1.pth" =
md5 of local `LOL_v2_real.pth` (6738bd02...). A 60-iteration probe from the CORRECT weights shows lr 2e-5 does not
harm the model (L1 on fixed crops 0.0491 → 0.0460), so the settings were kept. Fix: correct ID + an md5 assert in
every notebook. Invalid results archived in `results/_invalid_started_from_LOLv2real/` (with README).
Speed numbers (Day 2) are unaffected: same architecture and image size.
